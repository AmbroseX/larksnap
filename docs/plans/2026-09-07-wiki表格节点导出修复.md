# wiki 节点承载电子表格 / 多维表格的导出修复

> 复现链接：`https://yf2ljykclb.xfchat.iflytek.com/wiki/HzAXwivTUiHDrykp05grND8ozOh`
> 症状：CLI 与侧边栏都报「导出成功」，产出的 `.md` 只有一个换行符（1 字节）。
>
> 本文取代 `docs/plans/plan-loop-wiki-sheet-export/`（那份卡在「没有实测数据」，

## 一、实测数据（2026-09-07，profile 6gbmn78t，讯飞私有化租户）

探测手法：临时改 `src/content/index.ts` 的 `DETECT_DOC` 分支，在 content script 里
同源调 wiki 接口，结果 POST 到本机 19931 端口回传。用这条路是因为 **content.js 每次
`executeScript` 都从磁盘读，改了不用重载扩展**；background.js 不行。

`/space/api/wiki/v2/tree/get_node/` 的响应（字段名一字不差）：

```
obj_type      : 3
obj_token     : shtrzuUc5MtWN9bjdmnze0lE02b
wiki_node_type: 0
title         : 2026-Turing-星火智能体平台V2.2研发项目管理
可用字段      : space_id parent_wiki_token wiki_token obj_token obj_type title
                sort_id wiki_node_type origin_wiki_token origin_space_id
                origin_is_external origin_url has_child child_paging is_star url
                secret_key_delete is_explorer_star is_explorer_pin
                can_pre_heating entity_delete_flag icon_info detail_info
```

三条硬结论：

1. **`obj_type = 3` 就是电子表格**，`obj_token` 前缀 `sht` 独立印证同一件事。
   接口确实下发 `obj_type`，此前「响应里是否有该字段」的疑问到此为止。
2. **换 URL 走直链这条路死了**。拿真 obj_token 开
   `/sheets/shtrzuUc5MtWN9bjdmnze0lE02b`，服务端 302 跳回原 wiki 地址
   （探针在该次抓取里读到的 `location.pathname` 仍是 `/wiki/...`），产物照旧是
   1 字节空文件。旧方案里「改 URL 后报没有 spreadApp」的解读要更新：不是 token 错，
   是**服务端根本不让你停在直链上**。
3. **表格确实渲染在 wiki 主文档里**：主文档 `document.querySelectorAll('canvas').length === 6`，
   另有 3 个无 src 的动态 iframe。没有 CSP meta，也没有 CSP 违规事件。

一条没测到的：**wiki 壳里表格模型挂在哪个全局变量**。content script 注入的
inline script 与 blob script 都没执行（连第一行的回执都没发出来，且没有触发
`securitypolicyviolation`）。这是 content script 的限制，**不影响修复**——
`chrome.scripting.executeScript({world:'MAIN'})` 是特权注入，不受页面 CSP 约束，
现有 `exportSheet` 走的正是这条路。方案据此把全局变量做成自适应探测。

## 二、根因

三处只按 URL 路径判类型，`/wiki/<token>` 一律当 docx 处理：

- `src/content/feishu-detect.ts` 的 `PATH_TYPE_MAP`：`wiki` → `docType: 'wiki'`。
- `src/background/bridge.ts:526`：`doc.docType === 'sheets'` 才走 `exportSheet`。
- `src/background/actions-dispatch.ts:216`：同样只认 `'sheets'`。

于是 wiki 包的表格进了 docx 的 `client_vars` 管线。表格数据不在块里（走协同
WebSocket 进内存、画在 canvas 上），块树是空的，整条流程一路成功，落地一个空文件。

`resolveObjToken` 已经调了 `get_node`，但只取 `obj_token`，把 `obj_type` 丢了。

## 三、方案

### 3.1 只在能确定是表格时改道，其余一概不动

新增一个判定：wiki 节点解析出 `obj_type` / `obj_token` 后，只回答一个问题
「这是不是电子表格或多维表格」。

```
obj_type === 3  或 obj_token 以 sht 开头  → 电子表格
obj_type === 8  或 obj_token 以 bas 开头  → 多维表格
其余                                       → null，保持现有行为
```

双判据是因为只有 `3 = 电子表格` 经过实测，其它枚举值没有第一手数据；token 前缀
是飞书长期稳定的公开事实，两条互为兜底。返回 `null` 时走原来的 docx 管线，
**已经能用的文档一行行为都不变**，这是防回归的关键。

### 3.2 只改 docType，绝不改 token

判成表格后，把 `DocInfo.docType` 改写成 `sheets` / `base`，`token` 保持 wiki token。
理由：直链会被服务端跳回来（第一节结论 2），页面自始至终是 wiki 壳；而
`exportSheet` / `exportBitable` 读的是页面内存，压根不用 token。

### 3.3 表格模型全局变量做成自适应

现在 `extractWorkbookInPage` 只认 `window.spreadApp`。仓库里已有三种先例：
独立表格页 `spreadApp`、docx 内嵌表格块 `spread`、多维表格 `bitableStore`。
wiki 壳属于哪种没测到，所以按 `spreadApp` → `spread` 顺序探测，取到谁用谁；
两个都没有时，把页面上所有相关的全局变量名一并带进错误信息，让下一次真机验证
一次定位，不用再来一轮探测。

多维表格的 `bitableStore` 是全局单例，wiki 壳里同名的可能性高，同样加一轮轮询等待。

### 3.4 改动清单

| 文件 | 改什么 |
| --- | --- |
| `src/background/feishu-api.ts` | `ResolvedDoc` 加 `objType`；`resolveObjToken` 读 `obj_type`；新增 `resolveWikiDocType` |

## 四、顺带修掉的标题截断

第一次验证跑通后，文件名成了 `2026`。病根在页面内取标题的正则：

```
document.title.replace(/\s*[-–—].*$/, '')
```

本意是砍掉「 - 飞书云文档」后缀，但 `\s*` 能匹配 0 个空格，于是
「2026-Turing-星火智能体平台V2.2研发项目管理」被砍成了「2026」。改成
`/\s+[-–—]\s+.*$/`，只砍前后都带空白的分隔符。

中途试过「改用 DocInfo 的标题」，结果更差，拿到的是「函数公式」——
表格页上 `extractTitle()` 的 DOM 选择器命中了侧边面板一类的无关元素。
所以结论是**表格页的标题以 `document.title` 为准**，DocInfo 的只作兜底；
wiki 场景则让 `get_node` 的服务端标题优先，那是最权威的来源。

## 五、验证结果（2026-09-07 全部实测通过）

改的是 background.js。项目自带热重载（`vite.config.ts` 往产物里注入的那段），
后台脚本每秒比对 `manifest.json` 哈希，变了就 `chrome.runtime.reload()`。
但它**只在后台脚本活着的时候轮询**，而后台脚本空闲 30 秒就被回收，所以正确姿势是：
先跑一次抓取把它唤醒，趁这 30 秒改 `dist/manifest.json` 的 `_buildTime`，
它就会自己重载，不用手动去 chrome://extensions。
