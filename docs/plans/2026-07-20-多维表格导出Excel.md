# 多维表格（base）导出 Excel —— 实施方案

日期：2026-07-20
状态：待人工审查
修订：2026-07-21——第七节"记录接口兜底"降级为待验证假设（补虚拟化风险）；
里程碑 0 增补"导出对话框选项"探测项（官方可能自带附件打包，里程碑 3 或可免做）
前置调研：本仓 `src/background/exporters/export-task.ts`（docx 官方导出任务管线）、
`docs/plans/2026-07-09-采集入飞书多维表格.md`（bitable 内部接口背景）

## 一、要做成什么（第一性原理）

用户打开一个飞书多维表格（`/base/<token>`，或挂在知识库里的 `/wiki/<token>`），
点侧边栏一个按钮，把整个多维表格下载成一个 `.xlsx` 文件。就这一件事。

现状：`actions-dispatch.ts` 里 base 类型被全局挡掉（`UNSUPPORTED_EXPORT_TYPES`），
提示"暂不支持导出多维表格"。

## 二、技术路线：走官方导出任务接口（不自己拼 xlsx）

飞书网页版多维表格自带「下载为 Excel」菜单，走的是服务端导出。而本仓已经有一整套
官方导出任务管线（docx 导 PDF/Word 在用）：

```
createExportTask（POST /space/api/export/create/）
  → 轮询 fetchExportResult（GET /space/api/export/result/{ticket}）
  → 拿 file_token 走 downloadMedia 下载
  → downloadBase64 落盘
```

开放平台的对应接口（`drive/v1/export_tasks`）明确支持 `type: bitable` +
`file_extension: xlsx`，内部接口大概率是同一套后端，**只差 payload 里几个字段的取值**。
所以主路线就是：复用 `runExportTask`，让它支持 bitable。

为什么不自己读页面内存模型拼 xlsx（像电子表格 `sheet.ts` 那样读 `spreadApp`）：

1. bitable 前端模型和 sheets 完全不是一套，字段类型复杂（人员/关联/公式/附件），
   逆向成本高且随版本漂移；
2. 生成 xlsx 要引 SheetJS/exceljs 这类大依赖，扩展体积和维护成本都上去了；
3. 服务端导出的 xlsx 是官方转换，字段格式最忠实。

**代价**：租户关了导出权限（code 1002）时官方 xlsx 走不通。里程碑 1 先给明确提示，
但这正是 larksnap 的招牌场景，兜底方案（走记录接口/页面内存自己拼 CSV）见第七节。

## 三、里程碑 0：接口实测（必须先做，需要真机配合）

内部接口无公开文档，写代码前先在**已登录的真机浏览器**上，打开一个多维表格，
用 `feishu-doc-probe` 技能（或手动 DevTools）抓「下载为 Excel」的完整请求链，确认：

1. **create 请求**：路径是不是 `/space/api/export/create/`；payload 里 `type` /
   `file_extension` 的实际取值（推测 `type: 'bitable'` + `file_extension: 'xlsx'`，
   现有代码把两个字段都填成扩展名，对 bitable 多半不行——开放平台文档明确这俩
   字段含义不同）；有没有额外必填字段（如 `extra`、view/table 相关参数。开放平台
   的 CSV 导出必须传 `sub_id` 指定数据表，xlsx 未说明，内部接口可能有类似要求）；
   现有 payload 里的 `need_comment` 对 bitable 可能是无效字段，留意会不会报参数错。
2. **导出对话框的全部选项**：官方帮助文档显示导出多维表格时可选 .base / .xlsx /
   .csv，且可勾选"是否导出附件（附件单独打包为 .zip）"。把每个选项对应的
   payload 差异都录下来——**如果 create 接口自带附件开关，里程碑 3 整条自建
   附件管线就不用做了**，传个参数的事。
3. **轮询与产物**：result 接口和 ticket 结构是否与 docx 一致；`file_token` 下载
   URL 是否仍是 `download/all/{file_token}`，`mount_node_token` 传什么。
4. **wiki 挂载的 base**：`/space/api/wiki/v2/tree/get_node/` 返回里 bitable 的
   `obj_type` 数值（推测是 8，需确认），以及导出任务的 token 用 obj_token 是否可行。
5. **耗时**：中等规模表（几百行、多数据表）从 create 到 result 就绪要多久——
   决定轮询上限（现有 15 次 × 1s 对 docx 够用，bitable 大表可能不够）。
6. **各字段类型在导出 xlsx 里的形态**（用一张含图片/附件/人员/关联/公式字段的
   测试表导一次，打开看）：
   - 文本/数字/单选/多选/日期/公式：预期原样落成单元格文本，确认即可；
   - **图片/附件字段：预期官方导出只写文件名文本，不内嵌图片本体**——确认到底是
     文件名、URL 还是空白，这决定里程碑 3 的做法；
   - 人员/关联字段：确认落成什么文本（名字/记录标题）。

实测结论补写进本文档第十节后再动代码。探测不通（比如 bitable 走的是完全独立的
另一个域/另一套任务接口）就按实测形态调整封装方式，管线思路不变。

## 四、改动清单（里程碑 1：/base/ 直链导出）

按依赖顺序，全部是小改动：

1. **`src/shared/constants.ts`**：加 `MSG.EXPORT_EXCEL: 'export_excel'`。

2. **`src/background/feishu-api.ts`**：`createExportTask(token, fileExtension)` 加
   第三个可选参数 `objType`（默认不传保持现状，docx 路径零改动）：
   ```ts
   createExportTask(token, 'xlsx', 'bitable')
   // → POST /space/api/export/create/ { token, type: 'bitable', file_extension: 'xlsx', ... }
   ```
   具体字段以里程碑 0 实测为准。

3. **`src/background/exporters/export-task.ts`**：`runExportTask` 加可选
   `opts: { objType?, maxPolls? }`，bitable 用大一点的轮询上限（如 60 次 × 1s）。
   现有调用方不传，行为不变。

4. **`src/background/exporters/bitable.ts`（新文件，核心 ~60 行）**：
   ```
   exportBitable(doc):
     reportProgress 开始
     → runExportTask(doc.token, 'xlsx', { objType: 'bitable', maxPolls: 60 })
     → downloadBase64(base64, mime, `${safeName(title)}.xlsx`)
     → reportProgress 完成
   ```

5. **`src/background/actions-dispatch.ts`**：
   - `UNSUPPORTED_EXPORT_TYPES` 删掉 `base`；
   - 仿照 `blockSheetOnly` 加 `blockBaseOnly`：base 类型点 Markdown/PDF/HTML/附件时
     挡掉，提示"多维表格请用导出 Excel"；
   - 新增 `runExcelExport`：`requireReady` 校验后仅接受 base 类型，
     `withContentTab` 包裹调 `exportBitable`。

6. **`src/background/index.ts`**：注册 `case MSG.EXPORT_EXCEL`。

7. **侧边栏**（`src/sidepanel/actions.ts` + `ContextZone.tsx`）：
   - `ActionItem` 加可选 `docTypes?: FeishuDocType[]`（不填 = 全类型可见，现有项零改动）；
   - 新增 `excel` 动作项：`docTypes: ['base']`，msg 为 `MSG.EXPORT_EXCEL`；
   - 现有 4 个导出项标 `docTypes: ['docx', 'docs', 'wiki', 'sheets', 'file']`；
   - `ContextZone` 渲染前按 `doc.docType` 过滤——base 页只见「导出 Excel」，
     其他页看不到 Excel 按钮，比"点了报错"体验好。

8. **i18n**（`zh.ts` / `en.ts`）：`actions.excel.title/subtitle`、
   `progress.bitable.*`（导出中/轮询中/完成/失败）、被禁提示文案；
   `bg.unsupportedDocType` 的文案顺带更新（不再说"仅支持文档与电子表格"）。

## 五、里程碑 2（可选，实测后决定）：wiki 挂载的多维表格

知识库里的 base 地址是 `/wiki/<token>`，URL 识别为 `wiki` 类型，现在会走 docx 的
Markdown 管线然后失败（client_vars 对 bitable 是空的）。做法：

- `resolveObjToken` 已经调 `tree/get_node`，返回值加 `objType` 字段（数值来自实测）；

- 侧边栏 wiki 页仍显示 Markdown 等按钮（打开侧栏时不知道 obj 类型，不值得为按钮
  预发一次网络请求），点了自动转到 Excel 导出并在进度里说明。

先做里程碑 1 验证通路，这一步再上（KISS）。

## 六、图片与文字字段怎么处理（里程碑 3，可选）

**文字类字段**（文本/数字/单选/多选/日期/人员/公式）：服务端导出会转成单元格文本，
我们不用做任何事，xlsx 里直接可读。

**图片/附件字段**：官方 Excel 导出预期**不内嵌图片本体**（Excel 单元格本来也放不了
附件），最多落个文件名。

> ⚠️ 先看里程碑 0 第 2 项的探测结果：官方导出对话框本身可能就有"导出附件
> （单独打包 zip）"选项。若 create 接口带这个开关，**本节整条自建管线不用做**，
> 传参数即可；下面的方案仅在官方没有该选项时才作为备案。

要拿到图片/附件本体，兜底得单独走一条附件管线：

```
读 bitable 记录数据（内部记录接口，探测项与 2026-07-09 采集计划的里程碑 0 重合）
  → 收集附件字段里的 file_token
  → downloadMedia 逐个下载（复用现有，带登录态防盗链）
  → 与 xlsx 一起打 zip：《表名.xlsx》 + attachments/<数据表>/<记录标题>/<文件名>
```

产品形态：侧边栏「导出 Excel」默认只出 xlsx（快、够用）；附件打包做成第二个
按钮或选项「Excel + 附件（zip）」。这条管线依赖 bitable 记录读取接口的探测结果，
**不阻塞里程碑 1**——先让纯 xlsx 跑通，附件需求确认真实存在再上。

## 七、没有下载权限时怎么处理（关键设计）

"没权限"要拆成三种，应对完全不同——别混成一句"没权限"：

**A. 未登录（没身份，不是没权限）**
export_task 返回 403 / csrf error → `NotLoggedInError`。提示"请先登录飞书"。
这是身份缺失，登录后就有权限，不算真的没权限。

**B. 能打开表，但官方导出被禁**（管理员关了导出 / 你是只读协作者 / 文档带
"禁止下载"水印设置）→ export_task 返回 code 1002 no permission → `ExportDisabledError`。
**这是 larksnap 的主场**，也是它区别于"官方下载按钮"的核心价值：

> 关键洞察：**管理员关"导出"只关掉了 export_task 这个功能开关，表格数据本身
> 已经进了你的浏览器**（不然页面渲染不出来）。数据在，就有得读。

但要泼一盆冷水：**"数据进了浏览器"不等于"有一个能用 cookie 直接拉的 HTTP
记录接口"——这是待验证假设，不是已确认的事实。** 两个不利证据：

1. 本仓 `sheet.ts` 的注释已证实：电子表格的单元格数据**不走可拉取的 REST 接口**，
   而是通过协同 WebSocket 推到页面内存、画在 canvas 上。bitable 同属飞书协同
   架构，很可能一样；
2. 2026-07-09 采集计划里"记录增删改查的内部接口"至今也还是"待测"状态。

所以 B 的兜底思路成立（仿 docx 的 `markdown.ts`：`ExportDisabledError` 时自动
降级；bitable 的 client_vars 是空的，不能走 `runDecodeMd`），但**实现路径分三档，
按里程碑 0 的探测结果取其一**：

- **档一（最优）**：真有 HTTP 记录接口 → 直接拉全量记录拼 CSV：
  ```
  读 bitable 记录接口 → 拿到每张数据表的记录 + 字段
    → 拼成 CSV（零依赖，无权限场景不引 SheetJS，纯文本最稳）
    → 附件字段的 file_token 走 downloadMedia 下载（验证记录里的 token 是否受导出开关限制）
    → 打 zip：《表名》/<数据表>.csv + attachments/...
  ```
- **档二**：只有页面内存可读 → 仿 `sheet.ts` 在 MAIN 世界读内存 store。
  **必须直面虚拟化的坑**：bitable 前端是虚拟化渲染，内存里可能只有已加载的行，
  大表要模拟滚动逐段加载才能读全（钉钉文档逆向就是被"协同 WS + 虚拟化"判死
  的，见既往结论）。小表直接读；大表滚动加载做不稳就退档三。
- **档三（放弃）**：内存结构逆向成本过高或读不全 → 兜底不做，如实提示
  "该租户已关闭导出，且暂无可靠兜底"，不交付一个会悄悄丢行的产物。

产物退成 **CSV** 而不是 xlsx：自己拼 xlsx 要引依赖，而无权限兜底的价值在"能拿到数据"，
CSV 完全够用（和电子表格 `sheet.ts` 的产物一致）。

**C. 对这张表完全没有访问权**（打不开、页面提示"申请权限"）→ 数据根本没进你浏览器，
记录接口也会拒。**这种无解**，只能提示"你对该文档没有访问权限，请向所有者申请"。
不尝试任何绕过——没有数据可读，这是硬边界。

**降级链条**（`exportBitable` 的骨架，仿 `markdown.ts`）：
```
try 官方 xlsx（runExportTask）
  ├─ 成功 → 落 xlsx，结束
  ├─ NotLoggedInError → 提示登录（情况 A）
  └─ ExportDisabledError（情况 B）→ 按探测定档：档一记录接口 / 档二页面内存 → 拼 CSV zip 落盘
       ├─ 数据源也拒（情况 C）→ 提示"无访问权限，请申请"
       └─ 探测判为档三 → 提示"该租户已关闭导出"，不兜底
```

里程碑 1 先只做官方 xlsx + A/C 的清晰提示；B 的 CSV 兜底作为**里程碑 4（条件项，
探测通过才立项）**，依赖里程碑 0 对记录接口/页面内存的探测结果（与 2026-07-09
采集计划、里程碑 3 附件管线共用同一组接口探测），定档后再动手。

## 八、明确不做（YAGNI）

- 不自己拼 xlsx（不引 SheetJS 等依赖）；官方被禁时兜底产物用 CSV，不用 xlsx（第七节）；
- 不做按视图/按数据表选择性导出——官方整表导出是什么就是什么；
- 不做图片内嵌进 xlsx 单元格（格式不支持，伪需求）；附件本体走里程碑 3 的 zip 方案；
- 不做 bitable → Markdown（字段类型复杂，需求没出现；CSV 仅作无权限兜底产物）；
- bridge / larksnap-fetch CLI 侧暂不加 xlsx 导出命令（daemon 落地本地目录），
  等技能侧有真实使用场景再加。

| 风险 | 应对 |
| --- | --- |

测试表：`/base/basrzwjVokmx4OVQqBgtNZ7kfyf?table=tblSGe3lJ8GDnah1&view=vewLxqjFRD`
（看板视图，含 人员/单选标签/URL/文本 字段）
探测脚本：`.claude/skills/feishu-doc-probe/scripts/probe_bitable_subid.mjs`
（在已登录页面上下文用不同 payload 发 create，对比 HTTP 状态与 code）

### create 接口 payload（已坐实结构）

路径与 docx 一致：`POST /space/api/export/create/`。**有效 payload**：

```jsonc
{
  "token": "<base token>",        // /base/<token> 的 token
  "type": "bitable",              // 固定字符串，不是扩展名（这点计划第49行猜对了）
  "file_extension": "xlsx",       // 或 "csv"
  "sub_id": "<数据表 table id>",   // 必填！= URL 的 table=tbl... 参数
  "event_source": 1,             // 必填
  "need_comment": false          // 必填
}
```

判据（同一张表、同一账号，只改 payload）：

| payload | HTTP | code | 含义 |
| --- | --- | --- | --- |
| 全字段（上表） | **200** | **1002 no permission** | 格式正确，只是本账号无导出权限 |
| 有 sub_id，缺 event_source/need_comment | 400 | 2 Parameter Error | 缺必填字段 |
| 无 sub_id | 400 | 2 Parameter Error | 缺必填字段 |
| `type` 填 xlsx/sheet 等 | 400 | 2 Parameter Error | type 必须是 bitable |

**关键结论**：
1. `type` 恒为 `'bitable'`；现有 `createExportTask` 把 type 填成扩展名的写法对 bitable 不成立，必须加参数区分。
2. **`sub_id`（数据表 id）是必填**，官方导出是**按单张数据表**发起的，不是"整个 base 一次导出"。
   一个 base 有多张数据表时，"导出整表"要先拿到 table 列表再逐张 create（见下方待验证）。
3. `event_source`/`need_comment` 现有 docx payload 已带，bitable 同样必填，沿用即可。
4. HTTP 400(格式) vs 200+1002(权限) 的区分很干净：`runExportTask` 里 `isNotLoggedIn` 之外，
   1002 归 `ExportDisabledError` 的判断继续成立。

### 未能验证（本测试账号对该表只读，导出被禁 → 1002）

该账号点开文档级 `···` 菜单只有"申请编辑权限/导入"，**没有"导出"** —— 属计划第七节
**情况 B（能打开、官方导出被禁）**。因此拿不到成功样本，以下全部待有导出权限的表再测：

- **result/download 结构**：是否与 docx 完全一致（`data.result.file_token` → `download/all`）。
  计划假设一致，风险中等。
- **多数据表如何组织**：一次 create 带一个 sub_id 得到一个 xlsx。整个 base 多张表时——
  是"每张表一个 xlsx 各自下载"，还是某个 payload 能把所有表导成一个多 sheet 的 xlsx？
  **这直接决定里程碑 1 的封装**（单表 vs 枚举 table 列表逐张导）。需要先找到「列出 base 所有
  table」的内部接口（与 2026-07-09 采集计划的 bitable 元数据探测重合）。
- **附件选项**：`extra:{attachment:true}` / `need_attachment` 两个猜测字段因请求被 400 挡住
  没测到有效性，附件开关仍未知（里程碑 3 是否可省，取决于此）。
- **字段类型在 xlsx 里的形态**（里程碑 0 第 6 项）：人员/关联/附件字段导出后是文件名还是文本，未验证。

### 对里程碑 1 的影响（待用户定夺）

- payload 结构已够写代码，但"整表导出"到底是单表还是多表尚未落定，封装先按"单表(带 sub_id)"
  做最小可用，多表枚举留到拿到成功样本 + table 列表接口后再补。
- 本测试表恰是情况 B 的活标本：若优先验证兜底链（第七节档一/档二），可直接用它探测 bitable
  记录读取接口。但里程碑 1 的成功路径必须换一张**有导出权限**的表才能真机验证。

### 情况 B 兜底探测结论（2026-07-22 用 Playwright MCP 真机登录实测）

在已登录的 i讯飞私有化浏览器里，对本只读表命中 clientvars 接口，逐层解构：

- **clientvars 接口**：`GET /space/api/v1/bitable/{token}/clientvars?...` 返回 `code:0 success`，
  25KB。**服务器确实给只读用户下发了数据**（不是空骨架），但——
- **记录不在 REST 里**：`data.table` 与 `data.base` 都是 gzip+base64 字符串
  （`H4sI...` 是 gzip 魔数），**解压后就是字面量 `null`**。首屏 REST 不带任何记录。
  唯一有内容的是 `data.oldSchema`（22KB），但它只是**权限角色表**
  （`baseRoleMap`/`tableRoleMap`/`perm:0`），没有字段定义、没有记录。
- **记录走 WebSocket**：页面发了 `POST /space/api/pandora_ws/ws_ticket/` 建协同长连接，
  记录以 gzip+base64 二进制帧下发（页面里有 `unGzipBase64`/`base64ToUint8Array` 助手印证）。
  全量非静态请求里**没有任何 REST 记录接口**（无 ondemand/get_records）。

**判定：**
- **档一（HTTP 记录接口 → 拼 CSV）彻底不成立**。这个部署的 bitable 记录只在 pandora
  WebSocket 二进制帧里，没有能 cookie 直拉的 REST 接口。第七节"档一"作废。
- **档二（读页面内存）已实测跑通，且比预想干净**。用户拍板"档二读内存也做"，2026-07-22
  已在真机做完 POC：从内存把整表 17 条记录拼成完整 CSV（3856 字节），六种字段类型
  （文本/多行文本/单选/多选/人员/链接）全部正确落地。方案已固化，见下。

**档二实测方案（POC 已验证）：**

1. **定位数据根**（在 MAIN 世界执行，仿 `sheet.ts`）：
   ```
   base = window.bitableStore.services.find(s => s?.modelOperator?.base).modelOperator.base
   ```
   （不要写死 `services[1]`，索引会变，要按"带 modelOperator.base"找。）
2. **枚举表**：`base.blocks` 是数组，每个 block 是一张表。跳过 `fields` 为空的系统/空表
   （本例 block1 是 0 字段空表）。表名 `block.name`，表 id `block.id`。
3. **字段**：`block.fields` 是按 fieldId 存的**对象**（不是数组），元素 `{id, name, type, property}`。
   type：1=文本、3=单选、4=多选、11=人员、15=链接（其余类型未逐一测，靠通用序列化器兜住）。
4. **列顺序/可见性**：取网格视图（`block.views` 里 `type===1` 的）的 `view._visibleFieldIds`
   （有序、已过滤隐藏列）；无网格视图退回字段对象自身顺序。
5. **记录**：`block.records` 是按 recordId 存的对象，`block.recordsNum` 是总数。
6. **单元格 → 文本（关键）**：每个字段对象上都有序列化方法：
   - 优先 `field.cellValueToString(cell.value)`——文本/人员/链接/单选都给干净字符串；
   - 多选等没有它的，回退 `field.cellValueToStdValue(cell.value).data.map(d => d.text).join(', ')`。
   - `cellValueToStdValue` 是**唯一所有类型都有**的通用序列化器，返回 `{sourceType, data:[{text,…}]}`，
     所以最保险是"优先 cellValueToString，异常/无此方法则 stdValue"。**不用手写几十种字段类型**。
   - 单元格取值：`cell = block.records[recId][fieldId]`，值在 `cell.value`（可能是字符串/数组/对象，
     交给上面的序列化器，不要自己解）。
7. **组装**：CSV 转义 `/[",\n]/` 包双引号、内部 `"`→`""`。多表 → 每表一个 CSV 打包 zip，
   或用现有 xlsx 依赖合成多 sheet 的 .xlsx（跟里程碑 1 产物一致，体验统一，推荐）。

**唯一风险——懒加载**：本表 17 条全在内存（`recordsNum===records 键数`）。clientvars 带
`recordLimit=2000`，即首屏最多下发 2000 行；**超过 2000 行的大表内存里只有已加载部分**，
需触发全量加载（模拟滚动，或调 `AppendRecordsService`/`recordLoadedAreaManager` 相关接口，
待大表真机验证）。导出前必须校验 `Object.keys(block.records).length === block.recordsNum`，
不足则要么补齐、要么明确提示"仅导出已加载 N/M 行"，不静默截断（呼应第九节风险表）。

**辅助印证**：页面全局有 `unGzipBase64`/`base64ToUint8Array`（WS 帧是 gzip+base64）、
`BitableTestTool`（只是 canvas 坐标助手，非数据入口，别用）。
