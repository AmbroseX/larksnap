## 二、问题 1：怎么判断一个 `/wiki/` 链接包的是什么

有四种可能的判据，先摆代价和可靠性：

| 判据 | 代价 | 可靠性 | 什么时候会失效 |
|---|---|---|---|
| **A. URL query 参数**（`?sheet=` / `?table=&view=`） | 零。纯字符串解析，同步，可单测 | 高（参数在就一定准） | 从知识库目录树点进去时 URL 可能只有 `/wiki/<token>` 没有参数 |
| **B. 页面全局变量探测**（`spreadApp` / `spread` / `bitableStore`） | 一次 `executeScript`（几毫秒），需要已授权该域名 | **最高**——因为导出器要用的就是这个全局，探到了就一定导得出 | 页面还没加载完时三个全局都没有；表格若渲染在 iframe 里，只注主 frame 会漏 |
| **C. wiki API `obj_type`** | 两跳网络请求（`tree/get_info` + `tree/get_node`），最贵 | 高，但 `get_info` 在个人版/部分私有化会 PermFail（`feishu-api.ts:57` 的注释已记录过这个坑） | 网络失败、权限不足；且**知道类型也不等于导得出**，导出还是得读页面内存 |
| **D. DOM 特征**（找 `.sheet-tabs` 之类） | 一次注入 | 低，前端 class 名随版本漂移 | 不用 |

**选 A 作主判据 + B 作兜底，C 只用来生成准确的错误提示，D 不用。**

理由（第一性原理）：这次要的不是「这个 wiki 节点在服务端是什么类型」这个元数据事实，
而是「**当前这个标签页上有没有一个我能读出数据的表格模型**」。
后者才是导出能不能成的充要条件，而它的最直接判据就是 B。
A 的价值在于它免费且在页面没加载完时也准，所以拿来当快路径；
C 拿到的是元数据，回答不了「读不读得到」，所以只在 A、B 都判不出、需要给用户一句人话解释时才动用。

### 2.1 A 层：URL 参数判据（写在 `feishu-detect.ts`）

判据收得比较紧，避免误伤 wiki 包的普通 docx：

- `?sheet=<非空>` → `'sheet'`
- `?table=tbl...`（值以 `tbl` 开头）→ `'bitable'`
- 其余 → `undefined`（交给 B 层）

`tbl` 前缀有仓库内佐证：`docs/plans/2026-07-20-多维表格导出Excel.md:247` 记了实测地址
`/base/basrzwjVokmx4OVQqBgtNZ7kfyf?table=tblSGe3lJ8GDnah1&view=vewLxqjFRD`。
不校验 `view=vew` 是因为分享链接有时只带 `table` 不带 `view`（**待验证**，多带一个条件只会漏判，不会误判，所以按宽的写）。

**只在 `docType === 'wiki'` 时解析**。`/sheets/`、`/base/` 直链本来就靠路径判得准，
多解析一层没收益还多一份出错面。

### 2.2 B 层：全局变量探测（新文件 `wiki-kind.ts`）

只在「`docType === 'wiki'` 且 A 层没判出来」时才跑，所以 wiki 包普通文档最多多花一次几毫秒的注入。
探测用 `allFrames: true`，一次调用同时覆盖主 frame 和所有子 frame，代价和只注主 frame 一样，
顺手把「表格在 iframe 里」这种情况一并解决（见第三章情形 3）。

### 2.3 C 层：`obj_type`（本次**不实现**，只写清楚位置）

A、B 都判不出时，说明页面上确实没有可读的表格模型。
这时候即使查出 `obj_type` 是表格，也照样导不出，查它只能把错误提示从
「没读到内容」升级成「这是个电子表格，请等页面加载完再试」。
**收益是提示质量，不是功能**，按 YAGNI 本次不做，但把落点写死在这里备用：

`resolveObjToken()` 已经在调 `tree/get_node` 并读 `n?.obj_token`，
加一行 `objType: n?.obj_type != null ? Number(n.obj_type) : undefined` 到 `ResolvedDoc` 即可，
零额外请求。数值映射（22=docx 已确认，sheet / bitable 的值**待实测**）到时候再补。

## 三、关键未知：三种探测结果各自的实现路径

**动手写代码前必须先做这一步**。在复现链接的 wiki 页面控制台跑：

```js
// 主 frame
[typeof window.spreadApp, typeof window.spread, typeof window.bitableStore]

// 顺带看看有没有同源 iframe（情形 3 的关键线索）
[...document.querySelectorAll('iframe')].map(f => {
  try {
    const w = f.contentWindow;
    return [f.src.slice(0, 80), typeof w.spreadApp, typeof w.spread, typeof w.bitableStore];
  } catch { return [f.src.slice(0, 80), 'cross-origin']; }
})
```

三种结果对应三条路径。**情形 1 是主路径**（也是最可能的结果，因为 wiki 壳和 `/sheets/` 直链
在飞书里是同一套前端渲染，只是外面包了目录树），情形 2、3 是回退。

### 情形 1（主路径）：`window.spreadApp` 存在

**改动量最小，`sheet.ts` 一行不用改。**

`exportSheet(doc)` 从头到尾不使用 `doc.token`，只靠 `resolveTargetTabId()` 拿到目标 tab
再注入读 `window.spreadApp`。所以只要分流层把这个 doc 送进 `exportSheet`，当前页有 `spreadApp` 就能导。

这里有一个必须点明的时序前提：`runFeishuExport` 是在 `withContentTab(ctx.tabId, ...)` 里调 exporter 的，
`withContentTab` 会 `setContentTab(ctx.tabId)`，而 `resolveTargetTabId()` 第一行就是
`if (_contentTabId != null) return _contentTabId`。**所以探测用的 tab 和导出注入的 tab 必然是同一个**，
不会出现「在 A 页探到有表格，跑去 B 页导出」的错位。

多维表格同理：`exportBitable(doc)` 也只读 `window.bitableStore`，不碰 token。

### 情形 2（回退）：只有 `window.spread`，没有 `spreadApp`

`extractWorkbookInPage()` 现在的取模型方式是：

```ts
const app = (window as unknown as { spreadApp?: any }).spreadApp;
if (!app) return { ...EMPTY, error: '未找到表格应用实例（spreadApp）...' };
let cs: any, spread: any;
cs = app.collaborativeSpread;              // 用来 getActiveSheet()
spread = app.shell.viewModelManager.spread; // 用来列 sheets
```

注意 `app.shell.viewModelManager.spread` 很可能**就是** `window.spread`（**待验证**，
在控制台跑 `window.spread === window.spreadApp?.shell?.viewModelManager?.spread` 即可确认）。
如果成立，情形 2 缺的只是 `cs.getActiveSheet()` 这一个读数入口。

而 `extractEmbeddedSheets` 已经证明了**不需要 `getActiveSheet`**：
它直接对 `spread.sheets[]` 里的 sheet 对象调 `getRowCount() / getColumnCount() / getText(r, c)` 就能读出数据。

所以回退分支这么写：**保留现有 `spreadApp` 分支一个字不改**（它已在真机跑通，动它有回归风险），
只把 `if (!app) return error` 改成「进 `window.spread` 回退分支」：

```ts
// 位置：sheet.ts 的 extractWorkbookInPage 内，run() 开头
const app = (window as unknown as { spreadApp?: any }).spreadApp;
if (!app) {
  // 回退：wiki 壳等场景可能只有 window.spread（同 docx 内嵌表格块那套全局）。
  // 直接遍历 spread.sheets 逐张读，不依赖 getActiveSheet。
  const sp = (window as unknown as { spread?: any }).spread;
  if (!sp || !sp.sheets) {
    return { ...EMPTY, error: '未找到表格模型（spreadApp / spread 均不存在），页面可能未加载完成或不是电子表格' };
  }
  const out: { id: string; name: string; rows: string[][] }[] = [];
  for (const s of Array.from(sp.sheets as any[])) {
    let name = '';
    try { name = String(s.name()); } catch { /* 名字读不到不影响取数 */ }
    // 非激活的表数据可能还没经协同 WS 拉下来：点一下 tab 触发加载再轮询
    clickTab(name);
    let rows: string[][] = [];
    for (let i = 0; i < 8; i++) {
      rows = readSheetGrid(s);
      if (rows.length > 0 || i >= 4) break;
      await sleep(700);
    }
    out.push({ id: safeSheetId(s), name, rows });
  }
  return { title: pageTitle(), sheets: out };
}
```

配套要做的小重构（都在 `extractWorkbookInPage` 这个页内函数内部，仍然自包含）：

- 把现有 `readActive()` 里的读格逻辑抽成 `readSheetGrid(s)`（入参是 sheet 对象而非 `cs.getActiveSheet()`），
  `readActive()` 改成 `readSheetGrid(cs.getActiveSheet())` 再包上 id / name。**现有行为不变**。
- `clickTab(name)` 和标题提取原样复用，只是提到 `run()` 顶部好让两个分支都能调。
- `safeSheetId(s)` = `try { return String(s.id()) } catch { return '' }`，
  抄 `extractEmbeddedSheetsInPage` 里已有的 `typeof s.id === 'function'` 写法。

**风险**：回退分支里非激活 sheet 可能拉不到数据（点 tab 触发是尽力而为）。
兜底靠 `exportSheet` 已有的 `sheets.filter(s => s.rows.length > 0)`，
全空时会走 `t('progress.sheet.empty')` 报错，**不会静默出空文件**——这条已有逻辑正好接住。

### 情形 3（回退）：三个全局都没有

先分两种子情况处理，别急着上 `obj_type`：

**3a. 表格渲染在 iframe 里（最可能）。**
`exportSheet` / `exportBitable` 现在都是
`chrome.scripting.executeScript({ target: { tabId }, world: 'MAIN', func })`，
**默认只注入主 frame**。如果 wiki 壳把内容放进 iframe，主 frame 当然三个全局都没有。

解法：`probeWikiKind` 用 `allFrames: true` 探测，把命中的 `frameId` 一并带回；
`exportSheet` / `exportBitable` 加一个可选参数 `frameId`，注入时定向到那个 frame：

```ts
target: frameId != null ? { tabId, frameIds: [frameId] } : { tabId },
```

不传就是现在的行为，`/sheets/`、`/base/` 直链零影响。
`clickTab` 里的 `document.querySelector('.sheet-tabs')` 注进那个 frame 后自然指向该 frame 的 document，无需额外处理。

**3b. 页面确实还没加载完 / 这个 wiki 节点根本不是表格。**
此时 A 层 URL 参数一般也没命中，`wikiKind` 保持 `undefined`，
分流层按现状走 `exportMarkdown`（wiki 包普通文档的正常路径）。
如果它真是表格，`client_vars` 解出来是空的 —— 这时由第五章的空导出兜底把它变成一条明确的错误，
而不是像现在这样落一个空文件。这就是「不许静默失败」这条硬约束在情形 3 下的落点。

如果实测发现 3b 频繁出现（用户点得比页面加载快），再考虑加短轮询重探（如 3 次 × 800ms）。
**先不做**，等真出现再说（YAGNI）。

## 四、问题 2：`DocInfo` 怎么表达，以及连锁影响

### 4.1 加字段，不改 `docType`

```ts
// src/shared/types.ts，DocInfo 里追加
/**
 * wiki 节点实际承载的内容类型（只在 docType==='wiki' 时可能有值）。
 * 先由 URL 参数快判（?sheet= / ?table=tbl…），判不出再由页面全局变量探测补齐。
 * undefined = 当作普通文档处理。
 */
wikiKind?: 'sheet' | 'bitable';
```

**为什么不直接把 `docType` 改成 `'sheets'` / `'base'`？**

改 `docType` 看起来更省事（`blockSheetOnly` 之类一行都不用动），但会踩三个坑：

1. **`resolveObjToken` 会走错分支。** 它第一行就是
   `if (doc.docType !== 'wiki') return { objToken: doc.token, title: doc.title }`。
   把 wiki 的 `docType` 改成 `'sheets'` 之后，`doc.token` 是 **wiki_token 不是 obj_token**，
   会被当成 obj_token 直接用。表格导出这条路确实不碰它，但一旦以后有别的路径用到就是脏数据，
   属于埋雷。
2. **`editor.ts:78` 的白名单是 `['docx', 'wiki']`。** 改了 `docType` 会让本来能编辑的
   wiki 文档在某些边界下被误拒（虽然表格本来也编辑不了，但这个副作用是意料之外的）。
3. **`cache-manager.ts:22` 会把改过的 `docType` 存进缓存记录**，
   侧边栏 `CacheView.tsx:62` 直接显示它，用户会看到一个和 URL 对不上的类型。

加字段则**信息只增不减**：既知道「这是 wiki 节点」（token 解析链保持正确），
又知道「里面是表格」（分流依据）。两个事实各自独立，本来就该两个字段。

### 4.2 分流判据收成一个纯函数

三处分流点如果各写各的 `docType === 'sheets' || wikiKind === 'sheet'`，就是三份可以走岔的逻辑。
收成一个导出的纯函数，顺便好单测：

```ts
// src/background/actions-dispatch.ts
/**
 * 导出分流用的「实际内容类型」：把「/sheets/ 直链」与「wiki 壳里包的表格」
 * 归成同一件事，多维表格同理。分流点只认它，不再各自判 docType。
 */
export function effectiveKind(doc: DocInfo): 'sheet' | 'bitable' | 'doc' {
  if (doc.docType === 'sheets' || doc.wikiKind === 'sheet') return 'sheet';
  if (doc.docType === 'base' || doc.wikiKind === 'bitable') return 'bitable';
  return 'doc';
}
```

### 4.3 连锁影响逐条清点

| 位置 | 现状 | 改后 | 说明 |

 * 从 URL 参数判断 wiki 节点里包的是什么。
 * 电子表格：?sheet=<子表 id>；多维表格：?table=tbl…（&view=vew… 有时不带，不做必须项）。

export function wikiKindFromUrl(parsed: URL): DocInfo['wikiKind'] {

### 5.3 `src/background/wiki-kind.ts`（新建，约 45 行）

```ts
import type { DocInfo } from '../shared/types';

/**
 * wiki 壳页面上的表格模型探测（B 层判据）。
 *
 * 为什么要探：URL 上没有 ?sheet= / ?table= 参数时（比如从知识库目录树点进去），
 * 光看 URL 判不出这个 wiki 节点包的是文档还是表格。而「能不能导出」的充要条件
 * 就是页面上有没有对应的全局模型，所以直接探它最准。
 *
 * allFrames:true 是有意的：表格若渲染在 iframe 里，只注主 frame 会一无所获。
 * 命中的 frameId 一并带回，导出时定向注入那个 frame。
 */
export interface WikiKindProbe {
  kind: DocInfo['wikiKind'];
  /** 命中的 frame；主 frame 命中时为 0 或 undefined，导出按现状注主 frame */
  frameId?: number;
}

export async function probeWikiKind(tabId: number): Promise<WikiKindProbe> {
  try {
    const results = await chrome.scripting.executeScript({
      target: { tabId, allFrames: true },
      world: 'MAIN',
      func: probeInPage,
    });
    // 优先主 frame（frameId===0）的结果，避免被无关 iframe 抢先
    const hits = results.filter((r) => r.result);
    const main = hits.find((r) => r.frameId === 0) ?? hits[0];
    if (!main?.result) return { kind: undefined };
    return {
      kind: main.result as 'sheet' | 'bitable',
      frameId: main.frameId === 0 ? undefined : main.frameId,
    };
  } catch {
    // 注入失败（权限尚未生效、页面已关闭等）：当作判不出，走普通文档路径
    return { kind: undefined };
  }
}

/** 注入 MAIN world 执行，必须自包含。只做三个 typeof，不碰任何数据 */
function probeInPage(): 'sheet' | 'bitable' | null {
  const w = window as unknown as {
    spreadApp?: unknown;
    spread?: unknown;
    bitableStore?: unknown;
  };
  if (w.bitableStore) return 'bitable';
  if (w.spreadApp || w.spread) return 'sheet';
  return null;
}
```

**为什么先判 `bitableStore`**：多维表格页面里也可能挂着表格 SDK 的残留全局（**待验证**），
反过来电子表格页不会有 `bitableStore`，所以按「特异性从高到低」排序更稳。

/**

 * 返回补齐后的 doc 和命中的 frameId（主 frame 命中为 undefined）。
 * 非 wiki、或 URL 已经判出来了，都直接原样返回，不产生任何注入开销。

async function fillWikiKind(
  doc: DocInfo,
  tabId: number

  if (doc.docType !== 'wiki' || doc.wikiKind) return { doc };

## 六、问题 4：空导出兜底加在哪一层

先把候选层摊开比一比：

| 候选层 | 能看到什么 | 判不判得出「空」 | 结论 |
|---|---|---|---|
| `trackedExport` | 只有 `Response { success, error }` | **判不出**。它拿不到产物内容 | 不合适。硬要做就得改 Response 结构，牵动所有 exporter |
| `download.ts` 的 `downloadDataUrl` | 最终字节，是唯一的全局收口 | 判得出「字节少」，但**判不出「这算不算异常」** | 不合适。网页转 Markdown、用户真的导一篇空文档都走这里，加字节阈值会误伤 |
| **各 exporter 自查** | 转换前的结构化中间结果（markdown 串、images、sheetBlocks、tables） | **判得最准**，因为它知道「什么叫有内容」 | **选它** |

而且现状本来就是这个格局，只是覆盖不全：

- `sheet.ts:55-60`：`sheets.filter(s => s.rows.length > 0)`，全空则 `t('progress.sheet.empty')` 报错 ✅ 已有
- `bitable.ts:63-68`：`tables.filter(tb => tb.rows.length > 1)`，全空则 `t('progress.bitable.empty')` 报错 ✅ 已有
- `markdown.ts:131-139`：**只在 `loginHint` 有值时**才查空 ❌ 漏
- `html.ts`：完全不查 ❌ 漏（本 bug 的 1KB html 就是从这儿出来的）

所以要做的只有一件事：**把 markdown / html 这两条 client_vars 管线的空检查从条件生效改成无条件生效**，
逻辑抽成一个共用小函数避免两处走岔。
