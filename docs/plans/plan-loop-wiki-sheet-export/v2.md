## 〇、一句话结论

**不改 `docType`，给 `DocInfo` 加一个可选字段 `wikiKind`（`'sheet' | 'bitable'`）。**

填它的判据分两件互相独立的事，v1 把这两件事混成了一件，这是上一版最大的错：

1. **「这个 wiki 节点是什么」（分类）** —— 只信两个判据：URL 参数（`?sheet=` / `?table=tbl…`），
   和页面上**互斥的**全局变量 `window.spreadApp`（整页电子表格）/ `window.bitableStore`（多维表格）。
   **`window.spread` 绝对不能用来分类**：普通 docx 的内嵌表格块也挂在这个全局上
   （`sheet.ts:180` 的 `extractEmbeddedSheetsInPage` 就是读它），拿它分类会把
   「wiki 包的、含内嵌表格的普通文档」误判成整页表格，直接违反硬约束 2。
2. **「模型在哪个 frame」（定位）** —— 类型已经确定之后才做，此时才允许把 `spread`
   当作模型所在的证据。定位对 wiki 节点**无条件执行**，不因为 URL 已经判出类型就跳过，
   否则复现链接（自带 `?sheet=`）永远拿不到 frameId。

**分流收口成一个公共入口 `prepareFeishuDoc(tabId)`**，侧边栏的 5 个导出动作、小红书、
微信、附件、以及 CLI 桥接**全部**走它，不再各自 `detectDocForTab + blockXxxOnly`。

**空导出兜底覆盖每一个成功出口**，不只是 client_vars 解码那一条：
官方 Markdown、解码 Markdown、HTML、官方 PDF 四个出口各自在下载前自查，
表格导出区分「确认的空表」和「没读到的表」，后者一律进警告文案，不再被 `filter` 静默丢掉。

## 二、问题 1：怎么判断一个 `/wiki/` 链接包的是什么

### 2.0 先把「分类」和「定位」拆开（本版核心修正）

v1 把两个问题混成了一个函数 `probeWikiKind`，同时回答「是什么」和「在哪个 frame」，结果两头都出错：

- 用 `window.spread` 回答「是什么」 → 含内嵌表格的普通 wiki 文档被误判成整页表格（critical）。
- URL 已经答出「是什么」就整个跳过探测 → 「在哪个 frame」永远没人答（major）。

拆开之后规则很干净：

| | 分类：这个节点是什么 | 定位：模型在哪个 frame |
|---|---|---|
| 什么时候做 | wiki 且 URL 判不出时 | wiki 且已知/已判出是 sheet / bitable 时 |
| 认哪些信号 | `?sheet=` / `?table=tbl…`；`window.spreadApp`；`window.bitableStore` | sheet → `spreadApp` **或** `spread`；bitable → `bitableStore` |
| 为什么不认 `spread` | docx 内嵌表格块也挂 `spread`，它不具备区分力 | 类型已定，此时 `spread` 只回答「模型在这儿」，不承担分类职责 |

一次 `executeScript({ allFrames: true })` 把三个 `typeof` 全带回来，两个问题共用同一份原始数据，
分类和定位都是 SW 侧的**纯函数**，好单测（回应 r1 minor 第 7 条）。

### 2.1 四种判据的代价与可靠性

| 判据 | 代价 | 可靠性 | 什么时候失效 |
|---|---|---|---|
| **A. URL query**（`?sheet=` / `?table=tbl…`） | 零，纯字符串解析，同步，可单测 | 高（参数在就一定准） | 从知识库目录树点进去时可能只有 `/wiki/<token>` |
| **B. 全局变量**（`spreadApp` / `bitableStore`） | 一次 `executeScript`（几毫秒），需已授权该域名 | **最高**——导出器要用的就是这个全局，探到了就一定导得出 | 页面没加载完时都没有 |
| **C. wiki API `obj_type`** | 两跳网络（`tree/get_info` + `tree/get_node`） | 高，但 `get_info` 在个人版/部分私有化会 PermFail（`feishu-api.ts:57` 注释记录过） | 网络失败、权限不足；且**知道类型不等于导得出** |
| **D. DOM 特征**（找 `.sheet-tabs` 之类） | 一次注入 | 低，前端 class 名随版本漂移 | 不用 |

**选 A 作主判据 + B 作兜底，C 本次不实现（只写清落点），D 不用。**

理由（第一性原理）：这次要的不是「这个节点在服务端是什么类型」这个元数据事实，
而是「**当前这个标签页上有没有一个我能读出数据的表格模型**」——后者才是导出能不能成的充要条件，
它的最直接判据就是 B。A 免费且在页面没加载完时也准，当快路径。
C 拿到的是元数据，回答不了「读不读得到」。

r1 评审建议「最好用已验证的 `obj_type` 或可靠页面容器信号确认外层类型」——
`spreadApp` / `bitableStore` **就是**可靠的页面容器信号（它们与 `spread` 不同，docx 页面上不存在），
所以本版用它们即可满足 critical 的要求，不必为此引入两跳网络请求。见第十三章第 1 条的裁决说明。

### 2.2 A 层：URL 参数判据（写在 `feishu-detect.ts`）

判据收得紧，避免误伤 wiki 包的普通 docx：

- `?sheet=<非空>` → `'sheet'`
- `?table=tbl…`（值以 `tbl` 开头）→ `'bitable'`
- 其余 → `undefined`（交给 B 层）

`tbl` 前缀有仓库内佐证：`docs/plans/2026-07-20-多维表格导出Excel.md:247` 记了实测地址
`/base/basrzwjVokmx4OVQqBgtNZ7kfyf?table=tblSGe3lJ8GDnah1&view=vewLxqjFRD`。
不强制要求 `view=vew`，因为分享链接有时只带 `table`（**待验证**；多一个条件只会漏判不会误判，按宽的写）。

**只在 `docType === 'wiki'` 时解析**。`/sheets/`、`/base/` 直链靠路径判得准，多解析一层没收益。

### 2.3 B 层：全局变量探测（新文件 `wiki-model.ts`）

只对 `docType === 'wiki'` 跑，所以 `/docx/`、`/sheets/`、`/base/` 直链一次注入都不多花。
wiki 包的普通文档会多花一次几毫秒的注入（只做三个 `typeof`），可接受。

`allFrames: true` 是有意的：表格若渲染在 iframe 里，只注主 frame 会一无所获。
命中的 `frameId` 一并带回，导出时定向注入那个 frame。

### 2.4 C 层：`obj_type`（本次**不实现**，写清落点备用）

A、B 都判不出时，说明页面上确实没有可读的模型，这时即使查出 `obj_type` 是表格也照样导不出，
查它只能把错误提示从「没读到内容」升级成「这是个电子表格，请等页面加载完再试」。
**收益是提示质量，不是功能**，按 YAGNI 本次不做。落点写死在这里：

`resolveObjToken()` 已经在调 `tree/get_node` 并读 `n?.obj_token`，加一行
`objType: n?.obj_type != null ? Number(n.obj_type) : undefined` 到 `ResolvedDoc` 即可，零额外请求。
数值映射（22=docx 已确认，sheet / bitable 的值**待实测**）到时候再补。

## 三、关键未知：三种探测结果各自的实现路径

**动手写代码前必须先做第七章 7.0 的真机探测。** 三种结果对应三条路径，
情形 1 是主路径（也最可能，wiki 壳和 `/sheets/` 直链在飞书里是同一套前端渲染，外面只多了目录树）。

### 情形 1（主路径）：`window.spreadApp` 存在

**`sheet.ts` 的页内抽取器一行不用改**（只需加 `frameId` 参数和第六章的判空改造）。

`exportSheet(doc)` 从头到尾不使用 `doc.token`，只靠 `resolveTargetTabId()` 拿目标 tab 再注入读
`window.spreadApp`。所以只要分流层把这个 doc 送进 `exportSheet`，当前页有 `spreadApp` 就能导。

时序前提（必须点明）：`runFeishuExport` 在 `withContentTab(ctx.tabId, ...)` 里调 exporter，
`withContentTab` 会 `setContentTab(ctx.tabId)`，而 `resolveTargetTabId()` 第一行就是
`if (_contentTabId != null) return _contentTabId`。**所以探测用的 tab 和导出注入的 tab 必然是同一个**，
不会「在 A 页探到表格，跑去 B 页导出」。多维表格同理（`exportBitable` 也只读全局、不碰 token）。

### 情形 2（回退）：只有 `window.spread`，没有 `spreadApp`

**注意：这种情况下类型必须由 A 层（URL `?sheet=`）或 C 层确认，`spread` 自己不能当分类依据。**
如果 URL 上也没有 `?sheet=`，那本次就按普通文档走，由第六章的判空兜底给出明确错误——
不猜、不误伤（这是 critical 的直接落实）。

类型确认之后，`spread` 可以当抽取后端。现状取模型的写法（`sheet.ts:282-291`）：

```ts
const app = (window as unknown as { spreadApp?: any }).spreadApp;
if (!app) return { ...EMPTY, error: '未找到表格应用实例（spreadApp），页面可能未加载完成或不是电子表格' };
let cs: any, spread: any;
cs = app.collaborativeSpread;               // 用来 getActiveSheet()
spread = app.shell.viewModelManager.spread; // 用来列 sheets
```

`app.shell.viewModelManager.spread` 很可能**就是** `window.spread`（**待验证**，控制台跑
`window.spread === window.spreadApp?.shell?.viewModelManager?.spread`）。若成立，情形 2 缺的只是
`cs.getActiveSheet()` 这一个读数入口——而 `extractEmbeddedSheetsInPage` 已经证明**不需要它**：
直接对 `spread.sheets[]` 里的 sheet 对象调 `getRowCount() / getColumnCount() / getText(r,c)` 就能读。

所以回退分支这么写（**`spreadApp` 分支一个字不改**，它已在真机跑通，动它有回归风险）：

```ts
// 位置：sheet.ts 的 extractWorkbookInPage 内，run() 里 if (!app) 处
const app = (window as unknown as { spreadApp?: any }).spreadApp;
if (!app) {
  // 回退：wiki 壳等场景可能只有 window.spread（同 docx 内嵌表格块那套全局）。
  // 只有分流层已确认这是电子表格才会走到这里，所以不存在误判普通文档的问题。
  const sp = (window as unknown as { spread?: any }).spread;
  if (!sp || !sp.sheets) {
    return { ...EMPTY, error: '未找到表格模型（spreadApp / spread 均不存在），页面可能未加载完成或不是电子表格' };
  }
  const out: { id: string; name: string; rows: string[][]; ok: boolean }[] = [];
  for (const s of Array.from(sp.sheets as any[])) {
    let name = '';
    let id = '';
    try { name = String(s.name()); } catch { /* 名字读不到不影响取数 */ }
    try { id = typeof s.id === 'function' ? String(s.id()) : ''; } catch { /* 同上 */ }
    // 非激活的表数据可能还没经协同 WS 拉下来：点一下 tab 触发加载再轮询
    clickTab(name);
    let rows: string[][] = [];
    let read = false;   // 读格调用是否成功（区分「读失败」和「确认是空表」）
    let sized = false;  // 模型是否报得出行列数（报不出说明还没挂载好）
    for (let i = 0; i < 8; i++) {
      try {
        sized = s.getRowCount() > 0;
        rows = readSheetGrid(s);
        read = true;
      } catch {
        read = false;
      }
      if (read && (rows.length > 0 || i >= 4)) break;
      await sleep(700);
    }
    // ok 的判据：读格没抛异常，且「有数据」或「模型确实报了 0 行（真空表）」。
    // 读得到维度但一个字都没有 → 无法确认是真空表还是没加载完，标 false 让上层进警告，
    // 绝不和真空表塞进同一个桶被 filter 掉（r1 评审第 5 条）。
    out.push({ id, name, rows, ok: read && (rows.length > 0 || !sized) });
  }
  return { title: pageTitle(), sheets: out };
}
```

配套的小重构（都在 `extractWorkbookInPage` 这个页内函数内部，仍然自包含）：

- 把现有 `readActive()`（`sheet.ts:342-368`）里的读格逻辑抽成 `readSheetGrid(s)`
  （入参是 sheet 对象而非 `cs.getActiveSheet()`），`readActive()` 改成
  `readSheetGrid(cs.getActiveSheet())` 再包上 id / name。**现有行为不变**。
- `clickTab(name)`（`sheet.ts:301`）和标题提取（`sheet.ts:382-385`，抽成 `pageTitle()`）提到 `run()` 顶部，两个分支共用。
- **不碰 `extractEmbeddedSheetsInPage`**（它是独立函数，与本次无关）。

### 情形 3（回退）：三个全局都没有

**3a. 模型渲染在 iframe 里。**
`exportSheet` / `exportBitable` 现在都是 `executeScript({ target: { tabId }, world: 'MAIN', func })`，
**默认只注入主 frame**。若 wiki 壳把内容放进 iframe，主 frame 当然什么都没有。

解法：`probeFrames` 用 `allFrames: true`，`pickModelFrameId` 挑出模型所在 frame，
`exportSheet` / `exportBitable` 加可选参数 `frameId`，注入时定向：

```ts
target: frameId != null ? { tabId, frameIds: [frameId] } : { tabId },
```

不传就是现在的行为，`/sheets/`、`/base/` 直链零影响。
`clickTab` 里的 `document.querySelector('.sheet-tabs')` 注进那个 frame 后自然指向该 frame 的 document。

**3b. 页面确实还没加载完 / 这个节点根本不是表格。**
此时 A 层一般也没命中，`wikiKind` 保持 `undefined`，分流层按现状走 `exportMarkdown`（wiki 包普通文档的正常路径）。
如果它真是表格，`client_vars` 解出来是空的 —— 由第六章的判空兜底把它变成一条明确的错误，
而不是像现在这样落一个空文件。这就是「不许静默失败」在情形 3 下的落点。

如果实测发现 3b 频繁出现（用户点得比页面加载快），再考虑加短轮询重探（如 3 次 × 800ms）。
**先不做**（YAGNI）。

## 四、问题 2：`DocInfo` 怎么表达，以及连锁影响

### 4.1 加字段，不改 `docType`

```ts
// src/shared/types.ts，DocInfo 里追加
/**
 * wiki 节点实际承载的内容类型（只在 docType==='wiki' 时可能有值）。
 * 先由 URL 参数快判（?sheet= / ?table=tbl…），判不出再由页面全局变量探测补齐。
 * undefined = 当作普通文档处理。
 */
wikiKind?: 'sheet' | 'bitable';
```

**为什么不直接把 `docType` 改成 `'sheets'` / `'base'`？** 会踩三个坑：

1. **`resolveObjToken` 走错分支。** 它第一行是
   `if (doc.docType !== 'wiki') return { objToken: doc.token, title: doc.title }`。
   改了之后 `doc.token` 是 **wiki_token 不是 obj_token**，会被当成 obj_token 直接用。
   表格导出这条路确实不碰它，但别的路径一旦用到就是脏数据，属于埋雷。
2. **`editor.ts:78` 的白名单是 `['docx', 'wiki']`**，改 `docType` 会让本来能编辑的 wiki 文档在边界下被误拒。
3. **`cache-manager.ts:22` 会把改过的 `docType` 存进缓存记录**，侧边栏 `CacheView.tsx:62` 直接显示它，
   用户会看到一个和 URL 对不上的类型。

加字段则**信息只增不减**：既知道「这是 wiki 节点」（token 解析链保持正确），
又知道「里面是表格」（分流依据）。两个事实各自独立，本来就该两个字段。

### 4.2 分流判据收成一个纯函数

```ts
// src/background/actions-dispatch.ts
/**
 * 导出分流用的「实际内容类型」：把「/sheets/ 直链」与「wiki 壳里包的表格」
 * 归成同一件事，多维表格同理。所有分流点只认它，不再各自判 docType。
 */
export function effectiveKind(doc: DocInfo): 'sheet' | 'bitable' | 'doc' {
  if (doc.docType === 'sheets' || doc.wikiKind === 'sheet') return 'sheet';
  if (doc.docType === 'base' || doc.wikiKind === 'bitable') return 'bitable';
  return 'doc';
}
```

### 4.3 识别收口成一个公共入口（r1 评审第 3 条）

现状有**两套**并行的「识别 + 拦截」写法：
`actions-dispatch.ts` 里的 `runFeishuExport` / `runExcelExport` 是一套；
`index.ts:219 / 233 / 291`（小红书 / 微信 / 附件）自己 `detectDocForTab` + `requireReady` +
`blockSheetOnly` + `blockBaseOnly` 又是一套。只改前者，后者仍会把 wiki 表格当普通文档处理。

收口成一个导出函数，两边都用它：

```ts
// src/background/actions-dispatch.ts
export interface PreparedDoc {
  /** 已补齐 wikiKind 的文档信息；未识别时为 null */
  doc: DocInfo | null;
  /** 模型所在 frame（主 frame 或没探到时为 undefined，导出按现状注主 frame） */
  frameId?: number;
  /** requireReady 的结果：非 null 表示还没资格导出，调用方直接返回它 */
  error: Response | null;
}

/**
 * 所有按文档类型限流的导出入口的统一前置：识别 tab → 就绪校验 →
 * （只对 wiki）补齐承载类型与模型所在 frame。
 * 未就绪时**不做任何注入**（未授权私有化域名注不进去，白抛异常）。
 */
export async function prepareFeishuDoc(tabId: number): Promise<PreparedDoc> {
  const doc = await detectDocForTab(tabId);
  const error = requireReady(doc);
  if (error || !doc) return { doc, error };
  if (doc.docType !== 'wiki') return { doc, error: null };

  // wiki 节点：无条件探一次。
  // 即使 URL 已经判出 wikiKind，也必须探——否则拿不到模型所在 frame（r1 评审第 2 条）。
  const frames = await probeFrames(tabId);
  const kind = doc.wikiKind ?? pickWikiKind(frames);
  const filled = kind ? { ...doc, wikiKind: kind } : doc;
  return { doc: filled, frameId: pickModelFrameId(frames, effectiveKind(filled)), error: null };
}
```

### 5.3 `src/background/wiki-model.ts`（新建，约 60 行）

```ts
import type { DocInfo } from '../shared/types';

/**
 * wiki 壳页面上的模型探测。回答两个**互相独立**的问题：
 *   ① 这个 wiki 节点是什么（分类）—— 只认 spreadApp / bitableStore
 *   ② 模型在哪个 frame（定位）—— 类型已定后，sheet 也认 spread
 *
 * ⚠️ window.spread 不能用来分类：普通 docx 的内嵌表格块也挂这个全局
 * （见 sheet.ts 的 extractEmbeddedSheetsInPage），拿它分类会把「wiki 包的、
 * 含内嵌表格的普通文档」误判成整页表格，把正常的 Markdown 导出搞坏。
 *
 * allFrames:true 是有意的：模型若渲染在 iframe 里，只注主 frame 会一无所获。
 */
export interface FrameSignals {
  frameId: number;
  spreadApp: boolean;
  spread: boolean;
  bitableStore: boolean;
}

export async function probeFrames(tabId: number): Promise<FrameSignals[]> {
  try {
    const results = await chrome.scripting.executeScript({
      target: { tabId, allFrames: true },
      world: 'MAIN',
      func: probeInPage,
    });
    return results
      .filter((r) => r.result)
      .map((r) => ({ frameId: r.frameId ?? 0, ...(r.result as Omit<FrameSignals, 'frameId'>) }));
  } catch {
    // 注入失败（权限尚未生效、页面已关闭等）：当作什么都没探到，走普通文档路径
    return [];
  }
}

/** 注入 MAIN world 执行，必须自包含。只做三个 typeof，不碰任何数据 */
function probeInPage(): { spreadApp: boolean; spread: boolean; bitableStore: boolean } {
  const w = window as unknown as {
    spreadApp?: unknown;
    spread?: unknown;
    bitableStore?: unknown;
  };
  return { spreadApp: !!w.spreadApp, spread: !!w.spread, bitableStore: !!w.bitableStore };
}

/**
 * 分类（纯函数，可单测）：只认有区分力的两个全局。
 * bitableStore 优先——多维表格页面里也可能挂着表格 SDK 的残留全局（待验证），
 * 反过来电子表格页不会有 bitableStore，按「特异性从高到低」排序更稳。
 */
export function pickWikiKind(frames: FrameSignals[]): DocInfo['wikiKind'] {
  if (frames.some((f) => f.bitableStore)) return 'bitable';
  if (frames.some((f) => f.spreadApp)) return 'sheet';
  return undefined;
}

/**
 * 定位（纯函数，可单测）：类型已确定后，找模型所在 frame。
 * 主 frame（frameId===0）优先，避免被无关 iframe 抢先；主 frame 命中返回 undefined
 * （导出按现状注主 frame，与改动前完全一致）。
 */
export function pickModelFrameId(
  frames: FrameSignals[],
  kind: 'sheet' | 'bitable' | 'doc'
): number | undefined {
  const has = (f: FrameSignals) =>
    kind === 'bitable' ? f.bitableStore : kind === 'sheet' ? f.spreadApp || f.spread : false;
  const hits = frames.filter(has);
  if (hits.length === 0) return undefined;
  const pick = hits.find((f) => f.frameId === 0) ?? hits[0];
  return pick.frameId === 0 ? undefined : pick.frameId;
}
```

```ts
      // 多维表格只有 .xlsx 一条出路，而桥接协议对外只承诺 md/pdf/html
      //（skills/larksnap-fetch/SKILL.md 的用法与 fetch.mjs 的 --format 都是这三种）。
      // 与其回一个扩展名对不上的产物，不如明确告诉调用方去侧边栏导。
      res = { success: false, error: t('bg.bridgeBitableUnsupported') };
    } else if (contentKind === 'sheet') {
      // 电子表格：无论请求什么格式，都走内存抽取 → Markdown + CSV（打包 zip）
      res = await exportSheet(doc, frameId);
    } else if (fmt === 'pdf') res = await exportPdf(doc);
    else if (fmt === 'html') res = await exportHtml(doc);
    else res = await exportMarkdown(doc);
```

三点说明：

1. `doc` 本来就是 `let doc: DocInfo = info;`（第 484 行），可以重新赋值。
2. `tabId` 在第 470 行 `if (tabId == null) throw` 之后逻辑上必非空，
   但中间隔着 await，为省心直接写 `tabId!`。
3. **为什么 bitable 走「明确报错」而不是给 xlsx**：见第十三章第 4 条的裁决。
   顺带纠正一个现状认知——`/base/` 直链现在走的是 `exportMarkdown`，
   对多维表格解不出内容，产物本来就是空的/失败的；改成明确报错是把一个静默失败变成显式失败，
   不是把一个好功能改坏。

### 6.2 新增共用判据 `src/background/exporters/guard.ts`（新建，约 25 行）

```ts
import { base64ToBytes } from '../media-util';

/**
 * client_vars 管线的空产出判据：正文没字 + 一个素材都没有 = 这次导出啥也没解出来。
 * 常见成因：这个 token 根本不是 docx（wiki 壳里包的是表格/多维表格/画板），
 * 或私有文档匿名读不到。此时必须报错，绝不能落一个空文件让用户以为成功了。
 */
export function isBlankExport(markdown: string, assetCount: number): boolean {
  return !markdown.trim() && assetCount === 0;
}

/**
 * 官方导出产物的空判据（服务端生成的二进制，本地没有结构化中间结果可查）：
 *   - 任何格式：零字节 = 一定有问题
 *   - 文本格式（md）：额外看去掉空白后是不是一个字都没有（本 bug 的空 .md 就是这种）
 * 故意不设「字节数阈值」——短文档是合法的，只判「等于没有」。
 */
export function isBlankArtifact(base64: string, treatAsText: boolean): boolean {
  let bytes: Uint8Array;
  try {
    bytes = base64ToBytes(base64);
  } catch {
    return true; // 解不开的 base64 本身就是坏产物
  }
  if (bytes.length === 0) return true;
  if (!treatAsText) return false;
  return new TextDecoder().decode(bytes).trim() === '';
}
```

（`base64ToBytes` 是 `src/background/media-util.ts` 的既有导出，`markdown.ts` 已在用。）

| # | 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|---|

## 十三、r1 评审（codex / gpt-5.6-sol）逐条处置

> 处置前逐条打开了评审点名的源码核对，核对结论一并写在下面。

### 1. critical —— `window.spread` 被当成整页表格信号 → **采纳**

**核对结论：属实，而且是本方案最严重的错。**
`sheet.ts:180` 的 `extractEmbeddedSheetsInPage` 读的就是 `window.spread`
（函数头注释白纸黑字写着「docx 页的模型在 `window.spread`（不是 spreadApp）」）。
v1 的 `probeInPage` 写 `if (w.spreadApp || w.spread) return 'sheet'`，
会把「wiki 包的、含内嵌表格块的普通文档」判成整页表格，
Markdown 导出从 `exportMarkdown` 改走 `exportSheet` —— 正文全丢，直接违反硬约束 2。

**怎么改的**：把「分类」和「定位」拆成两个问题（第 2.0 节）。

- 分类只认 `spreadApp` / `bitableStore`（`pickWikiKind`），**`spread` 一票都没有**；
- 定位在类型已定之后才做，那时 `spread` 才作为「模型在这个 frame」的证据（`pickModelFrameId`）；
- 情形 2 的 `spread` 抽取回退保留，但明确写死「只有 URL/API 已确认是 sheet 才会走到这里」（第三章）。

**对建议的一处偏离**：评审建议「最好用已验证的 `obj_type` 或可靠页面容器信号确认外层类型」，
本版选后者——`spreadApp` / `bitableStore` 就是可靠的页面容器信号（docx 页面上不存在它们），
用它们零网络开销就能满足要求，不必为此引入 `tree/get_info` + `tree/get_node` 两跳请求
（且 `get_info` 在个人版/部分私有化会 PermFail，`feishu-api.ts:57` 有记录）。`obj_type` 仍写在 2.4 节备用。

**回归锁**：`wiki-model.test.ts` 里「只有 spread → undefined」这条；
`actions-dispatch.test.ts` 里「探测判不出 → 走 exportMarkdown」这条；真机 R3。

### 2. major —— `fillWikiKind` 早返回导致拿不到 frameId → **采纳**

**核对结论：属实。** v1 的 `fillWikiKind` 第一行 `if (doc.docType !== 'wiki' || doc.wikiKind) return { doc }`，
而复现链接自带 `?sheet=fakwBh`，A 层直接判出 `wikiKind='sheet'` → 探测被跳过 →
`frameId` 永远是 `undefined` → 情形 3（模型在 iframe）的整套方案在**最主要的那个 URL 上根本不生效**。

**怎么改的**：`prepareFeishuDoc`（4.3 节）对 wiki 节点**无条件探一次**，
`kind = doc.wikiKind ?? pickWikiKind(frames)`（URL 优先），
`frameId = pickModelFrameId(frames, effectiveKind(filled))`（永远算）。
代价是每次 wiki 导出多一次只做三个 `!!` 的注入，写进风险表第 8 条。

评审给的另一个选项「让 exporter 自己在所有 frame 中查找并只执行一次抽取」没选：
`extractWorkbookInPage` 会点 tab、轮询、读全表，把它 `allFrames` 铺开跑风险大得多
（多个 frame 同时点 tab、多份结果要合并）。**先定位、再单点抽取**更符合 KISS。

**回归锁**：`actions-dispatch.test.ts` 的「wikiKind 已由 URL 判出时仍然会探测」
和「探到的 frameId 会传给 exportSheet / exportBitable」三条。

### 3. major —— 小红书 / 微信 / 附件三个入口绕开新判据 → **部分采纳**

**核对结论：属实。** `index.ts:219 / 233 / 291` 三处确实是
`detectDocForTab` + `requireReady` + `blockSheetOnly` + `blockBaseOnly` 的手写组合，
完全不经过 `dispatchAction`，v1 只改了 `actions-dispatch.ts` 里的两个函数。

**采纳的部分**：把「识别 + 就绪校验 + 补齐 effective kind」收口成
`prepareFeishuDoc(tabId)`（4.3 节），三个入口全部改用它（5.5 节），
`runFeishuExport` / `runExcelExport` 也用同一个，`bridge.ts` 用同一套纯函数。
以后再加导出动作，抄这一行就不会漏。

**没采纳的部分**：评审要求「相关测试也要覆盖无 query 的探测结果」——
无 query 的探测结果在 `actions-dispatch.test.ts` 和 `wiki-model.test.ts` 里都覆盖了，
但**没有为 `index.ts` 那三个入口写单测**：`index.ts` 是 SW 顶层消息路由，
仓库里没有它的测试基座（`src/**/*.test.ts` 共 11 个，一个都不测 `index.ts`），
为三条 case 现搭一套 mock 不划算。改用「结构保证 + 真机验证」：
三个入口调的是同一个 `prepareFeishuDoc`（收口本身就是防错），
真机用 7.1 第 4 条（在 wiki 表格页点附件 / 小红书 / 公众号，看是否被挡）验收。

### 4. major —— 桥接对 bitable 忽略 `fmt` 返回 `.xlsx` → **采纳**

**核对结论：基本属实，但有一处事实需要更正。**

属实的部分：`skills/larksnap-fetch/SKILL.md:38` 的用法确实写死
`[--format md|pdf|html]`，`fetch.mjs:38` 也只是 `flag('--format','md')` 透传、不做校验；
`fetch.mjs:143` 的 `folderNameFrom()` 只剥 `zip|md|markdown|pdf|html?` 后缀，
一个 `.xlsx` 产物会落成 `<标题>.xlsx/<标题>.xlsx` 这种莫名其妙的目录结构。
调用方要 md 却收到 xlsx，确实不可接受。

需要更正的部分：评审说这会「改变 `/base/` 直链的现有桥接行为」——
`/base/` 直链现在走的是 `exportMarkdown`（`docType==='base'` 不等于 `'sheets'`），
而多维表格的记录压根不在 `client_vars` 里（`bitable.ts` 头注释：解压后是字面量 null），
所以**现状本来就是产出空的/失败的**，不存在一个被改坏的好行为。

**怎么改的**：按评审的第一个建议，桥接侧对 `effectiveKind === 'bitable'` 直接返回
`t('bg.bridgeBitableUnsupported')`（5.8 节），文案指路侧边栏。
这既避免了扩展名对不上的坏产物，也把一个静默失败变成了显式失败（硬约束 4）。
真要支持 xlsx 得同步改 `fetch.mjs` 的 `--format` 校验、`folderNameFrom`、`SKILL.md`
和退出码语义 —— 那是另一个需求，本次不做（YAGNI）。验收看 R11。

### 5. major —— `spread` 回退里读失败的表被静默丢弃 → **采纳**

**核对结论：属实，且问题比评审说的更大。**
`sheet.ts:55` 的 `wb.sheets.filter((s) => s.rows.length > 0)` 把「没读到」和「真空表」
塞进同一个桶，只要有一张表有数据就报完整成功。v1 还把这个当成「可接受的降级」写进风险表第 8 条——
这确实是硬约束 4 的正面违反。

**更大的问题（评审没提到，本版一并修）**：现有 `spreadApp` 主路径的循环（`sheet.ts:371-380`）
在切表失败（`countTop` 一直 `ready:false`）时**仍然无条件调 `readActive()`**，
读回来的是**当前 active 那张表**的数据 —— 也就是把上一张表的内容重复写进这一张，
产出的是**错数据**，比空数据更坏。这条 `/sheets/` 直链现在就可能踩到。

**怎么改的**（5.6 节）：抽取结果每张表加 `ok` 标记。

- `spreadApp` 路径：切不过去 → `{ rows: [], ok: false }`，不再拿别的表冒充；
- `spread` 回退：读格抛异常，或「读得到但一个字都没有且模型报得出行数」→ `ok: false`；
- SW 侧结算：一张能确认的表都没有 → 报错（区分 `unreadable` / `empty` 两种文案）；
  有表没读到但另有表有数据 → **照样出 zip，但成功文案点名「未读到：X、Y」**。

选了评审给的第二个选项（明确的部分导出警告）而不是第一个（整体失败）：
仓库已有先例——`bitable.ts` 行数不全时「照出但提示 N/M 行」，`markdown.ts` 图片部分失败时
`doneWithPartialImages`。整体失败会让「10 张表里有 1 张没加载完」变成一个字都拿不到，
过度惩罚。判据偏保守（真空表也可能被算进警告）已写进风险表第 5 条。

### 6. major —— 判空只覆盖 client_vars 路径，官方 md 出口漏了 → **采纳**

**核对结论：属实。** `markdown.ts:81-99` 的 `runOfficialMd` 是
`runExportTask` → `downloadBase64(result.base64, …)` 直下，中间**没有任何判空**；
`html.ts:66-70` 同样全程不判。v1 说「堵住了这一整个类别」是夸大了。

**怎么改的**（第六章）：逐个成功出口列表盘点，四个出口全部加自查。

- `guard.ts` 加第二个判据 `isBlankArtifact(base64, treatAsText)`：零字节一律算空，
  文本格式额外看 `trim()` 后是不是一个字都没有（本 bug 那个「只有一个换行」的 md 正好命中）；
- `runOfficialMd` 下载前查（文本模式）；
- `runDecodeMd` 的判空从「只在 `loginHint` 有值时」改成无条件；
- `html.ts` 生成前查（注意它的 `blocksToMarkdown` 解构里没有 `whiteboards`，别照抄）；
- `pdf.ts` 加零字节检查（v1 说「pdf 不用加」，评审要求各出口都覆盖，一行的事，收下）。

按评审要求**不设统一字节阈值**——短文档是合法的，只判「等于没有」。

### 7. minor —— 测试没覆盖 frameId 传递、多 frame 选择、`spread` 误判、guard 接线 → **部分采纳**

**核对结论：属实，而且 v1「`probeWikiKind` 不值得单测」的理由确实不成立**——
它包含本次最关键的分类逻辑，正是 critical 出错的地方。

**采纳的部分**：把探测拆成「薄 chrome 包装 + 两个纯函数」就是为了能测。

只有 `spread` 不分类 / `bitableStore` 优先 / 注入失败返回空数组；
`actions-dispatch.test.ts` 新增「frameId 传给 exportSheet / exportBitable」的断言；
新建 `guard.test.ts` 覆盖两个判据的边界。

**没采纳的部分**：评审要求「为 guard **及其调用位置**增加测试」——

（11 个测试文件里没有 `exporters/` 下的任何一个），为它们现搭 mock 要连带假造

### 两条意见冲突时的裁决

r1 的第 1 条（`spread` 不能分类，普通文档必须继续走文档管线）和第 5 条
（`spread` 回退里读不到的表不能静默丢）表面上都指向「少信 `spread`」，
但落点不同，本版分开处理、没有各改一半：

- **第 1 条管「进不进这个分支」**：`spread` 对分类零投票权，
  只有 URL/API 已确认是 sheet 才允许进 `spread` 抽取分支；
- **第 5 条管「进来之后怎么算成败」**：进来了也不能默认读得到，
  每张表都要带 `ok` 标记，读不到就必须在结果里说出来。

两条叠加的净效果是：`spread` 从「一个会误判类型、又会静默丢数据的信号」，
降级成「一个只在类型已知时用、且必须自证读到了什么的抽取后端」。
