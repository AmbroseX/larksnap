## 〇、结论与改动地图

**不改 `docType`，给 `DocInfo` 加可选字段 `wikiKind`（`'sheet' | 'bitable'`）。** 三条主线：

3. **空导出兜底覆盖每个成功出口**，按 `ls exporters/` 的 13 个文件逐个盘点、逐个给结论。

## 二、怎么判断 `/wiki/` 链接包的是什么

### 2.1 分类 vs 定位

| | 分类：这节点是什么 | 定位：模型在哪个 frame |
|---|---|---|
| 何时做 | wiki 且 URL 判不出时 | wiki 且已知/已判出是 sheet / bitable 时 |
| 认哪些信号 | `?sheet=` / `?table=tbl…`；`spreadApp`、`bitableStore`（**都要结构确认**） | sheet → `spreadApp` 或 `spread`；bitable → `bitableStore` |
| 为何不认 `spread` | docx 内嵌表格块也挂它，零区分力 | 类型已定，此时它只回答「模型在这儿」 |

一次 `executeScript({ allFrames: true })` 把信号全带回来，两个问题共用同一份数据；两个判定函数都是 SW 侧纯函数，好单测。

### 2.2 四种判据的代价与可靠性

| 判据 | 代价 | 可靠性 / 何时失效 |
|---|---|---|
| **A. URL query** | 零，纯字符串，可单测 | 高；从目录树点进去可能只有 `/wiki/<token>` |
| **B. 全局变量 + 结构确认** | 一次 `executeScript`（几毫秒），需已授权域名 | **最高**——导出器要用的就是这个模型，探到了就一定导得出；页面没加载完时都没有 |
| **C. wiki API `obj_type`** | 两跳网络（`tree/get_info` + `tree/get_node`） | 高，但 `get_info` 在个人版/部分私有化会 PermFail（`feishu-api.ts:57` 有注释）；且知道类型≠导得出 |
| **D. DOM 特征**（找 `.sheet-tabs`） | 一次注入 | 低，class 名随版本漂移。不用 |

**选 A 主判据 + B 兜底，C 不实现（写清落点与启用条件），D 不用。** 理由：要的不是「服务端元数据是什么」，
而是「**当前页上有没有一个我能读出数据的模型**」——后者才是导出能否成功的充要条件，直接判据就是 B；
A 免费且页面没加载完时也准，当快路径。

### 2.3 A 层：URL 参数

`?sheet=<非空>` → `'sheet'`；`?table=` 值以 `tbl` 开头 → `'bitable'`（佐证：
`docs/plans/2026-07-20-多维表格导出Excel.md:247` 的实测地址 `/base/basrz…?table=tblSGe3lJ8GDnah1&view=vewLxqjFRD`）；
其余 → `undefined` 交给 B 层。不强制同时带 `view=vew`（分享链接有时只带 `table`，**待验证**；
多一个条件只会漏判不会误判，按宽的写）。**只在 `docType === 'wiki'` 时解析**，直链靠路径判得准。

### 2.4 B 层：全局变量 + **结构确认**

只对 wiki 跑，直链一次注入都不多花。`allFrames: true` 是有意的：模型若在 iframe 里，只注主 frame 一无所获。

**光看 `typeof` 不够（r2 MAJOR-1）**：飞书 docx 可以内嵌多维表格视图块，那类页面上会不会也挂着
`window.bitableStore` **从未验证过**。一旦挂着而我们只看「有没有」，正常 wiki 文档会被判成 bitable，
`blockBaseOnly` 在 `runFeishuExport` 的**最前面**（`actions-dispatch.ts:211`，在 `withContentTab` 之前）
直接返回 `bg.baseOnlyExcel`，**md / pdf / html / 附件四个导出全被挡死**，硬约束 2 正面被破。

所以页内探测顺手做结构确认（判据抄现成代码，各一行）：`bitableStore` 要在 `services` 里找得到
`modelOperator.base` 且 `base.blocks` 非空（抄 `bitable.ts:140-146`）；`spreadApp` 要
`shell.viewModelManager.spread.sheets.length > 0`（抄 `sheet.ts:284-296`）。内嵌视图块不会挂一整个 base 模型，
这样天然区分开。代价：探测函数从 3 行变 20 行，零额外网络请求。

### 2.5 C 层：`obj_type`（不实现，写清落点 + 启用条件）

A、B 都判不出说明页面上确实没有可读模型，此时即使查出 `obj_type` 是表格也照样导不出，
查它只能把提示从「没读到内容」升级成「这是电子表格，请等页面加载完」——**收益是提示质量不是功能**，YAGNI。

落点：`resolveObjToken()` 已经在调 `tree/get_node` 并读 `n?.obj_token`，加一行
`objType: n?.obj_type != null ? Number(n.obj_type) : undefined` 到 `ResolvedDoc` 即可，零额外请求。

**启用条件（唯一会改变骨架的探测分叉）**：7.0 页面 C 若探到「含内嵌 bitable 视图块的 docx 上也挂着结构完整的
`bitableStore`」，说明 §2.4 的结构确认不够，**必须启用 C 层**给 bitable 分支做二次确认，
同时实测 sheet / bitable 的 `obj_type` 数值。

## 三、三种探测结果各自的实现路径

**动手前必须先跑 §7.0。** 情形 1 最可能（wiki 壳和 `/sheets/` 直链是同一套前端渲染）。

### 3.1 情形 1（主路径）：`spreadApp` 存在

**页内抽取器一行不用改**（只需 `frameId` 参数 + 第六章的判空改造）。
`exportSheet(doc)` 全程不用 `doc.token`，靠 `resolveTargetTabId()` 拿 tab 再注入读 `window.spreadApp`。

时序前提：`runFeishuExport` 在 `withContentTab(ctx.tabId, …)` 里调 exporter，`withContentTab` 会
`setContentTab(ctx.tabId)`，而 `resolveTargetTabId()` 第一行是 `if (_contentTabId != null) return _contentTabId`
（`feishu-proxy.ts:49-50`）。**探测用的 tab 和导出注入的 tab 必然是同一个**，不会「在 A 页探到、跑去 B 页导」。
`exportBitable` 同理。

### 3.2 情形 2（回退，=B1）：只有 `window.spread`

**类型必须由 A 层（URL `?sheet=`）确认，`spread` 自己不能当分类依据。** URL 上也没有就按普通文档走，
由第六章判空兜底给明确错误——不猜、不误伤。

`app.shell.viewModelManager.spread` 很可能**就是** `window.spread`（**待验证**）。若成立，情形 2 缺的只是
`cs.getActiveSheet()` 这一个读数入口——而 `extractEmbeddedSheetsInPage` 已证明**不需要它**：
直接对 `spread.sheets[]` 的 sheet 对象调 `getRowCount() / getColumnCount() / getText(r,c)` 就能读。

新增分支放在 `extractWorkbookInPage` 内 `run()` 里 `if (!app)` 处，**`spreadApp` 分支的取模型逻辑一字不改**：

```ts
const sp = (window as unknown as { spread?: any }).spread;
if (!sp || !sp.sheets) return { ...EMPTY, error: '未找到表格模型（spreadApp / spread 均不存在）…' };
const out: { id: string; name: string; rows: string[][]; ok: boolean }[] = [];
for (const s of Array.from(sp.sheets as any[])) {
  let name = '', id = '';
  try { name = String(s.name()); } catch {}
  try { id = typeof s.id === 'function' ? String(s.id()) : ''; } catch {}
  // 名字读不到就别点：clickTab('') 的兜底选择器会命中页面第一个空叶子元素并派五连击（sheet.ts:305-307）。
  // 不点也能读——extractEmbeddedSheetsInPage 已证明。
  if (name) clickTab(name);
  // ok 判据：模型在、维度报得出 = 确认读到了（哪怕一个字都没有，那是真空表）；
  // 维度都读不出 = 没挂载好，数据不可信。绝不用「有没有数据」当判据（见 §13 MAJOR-4）。
  let dims = false, rows: string[][] = [];
  for (let i = 0; i < 8; i++) {
    try { s.getRowCount(); s.getColumnCount(); dims = true; rows = readSheetGrid(s); } catch { dims = false; }
    if (dims && (rows.length > 0 || i >= 4)) break;
    await sleep(700);
  }
  out.push({ id, name, rows, ok: dims });

return { title: pageTitle(), sheets: out };
```

配套小重构（都在 `extractWorkbookInPage` 内部，仍自包含，**现有行为不变**）：
`readActive()`（`sheet.ts:342-368`）的读格逻辑抽成 `readSheetGrid(s)`（入参是 sheet 对象），
`readActive()` 改成 `readSheetGrid(cs.getActiveSheet())` 再包 id / name；
`clickTab`（301 行）和标题提取（382-385 行，抽成 `pageTitle()`）提到 `run()` 顶部两分支共用；
**不碰 `extractEmbeddedSheetsInPage`**（独立函数，与本次无关）。

### 3.3 情形 3（回退）：三个全局都没有

**3a. 模型在 iframe 里。** 两个 exporter 现在是 `executeScript({ target: { tabId }, … })`，**默认只注主 frame**。
解法：`probeFrames` 用 `allFrames: true`，`pickModelFrameId` 挑出 frame，exporter 加可选 `frameId`：
`target: frameId != null ? { tabId, frameIds: [frameId] } : { tabId }`。不传就是现在的行为，直链零影响。
`clickTab` 里的 `document.querySelector('.sheet-tabs')` 注进那个 frame 后自然指向该 frame。

**3b. 页面没加载完 / 这节点根本不是表格。** A 层一般也没命中，`wikiKind` 保持 `undefined`，按现状走
`exportMarkdown`。若它真是表格，`client_vars` 解出来是空的 —— 由第六章判空兜底变成明确错误而不是落空文件，
这就是「不许静默失败」在情形 3 下的落点。若实测发现 3b 频繁出现，再加短轮询重探（3 次 × 800ms）。**先不做**。

## 四、`DocInfo` 怎么表达，连锁影响是什么

### 4.1 加字段，不改 `docType`

```ts
// shared/types.ts 的 DocInfo 里追加
/** wiki 节点实际承载的内容类型（只在 docType==='wiki' 时可能有值）。
 *  URL 参数能判就先判，判不出再靠页面模型探测补齐。undefined = 按普通文档处理。 */
wikiKind?: 'sheet' | 'bitable';
```

**为什么不直接改 `docType`**——三个坑：① `resolveObjToken` 第一行
`if (doc.docType !== 'wiki') return { objToken: doc.token, … }`，改了之后把 **wiki_token 当 obj_token** 用
（表格这条路不碰它，但属于埋雷）；② `editor.ts:78` 白名单是 `['docx','wiki']`，改了会让本来能编辑的 wiki
文档被误拒；③ `cache-manager.ts:22` 把 `docType` 存进缓存、`CacheView.tsx:62` 直接显示，用户看到和 URL
对不上的类型。加字段则信息只增不减：既知道「这是 wiki 节点」（token 解析链保持正确），又知道「里面是表格」。

### 4.2 分流判据收成纯函数（放 `wiki-model.ts`）

```ts
/** 把「/sheets/ 直链」与「wiki 壳里包的表格」归成同一件事，多维表格同理。所有分流点只认它。 */
export function effectiveKind(doc: DocInfo): 'sheet' | 'bitable' | 'doc' {
  if (doc.docType === 'sheets' || doc.wikiKind === 'sheet') return 'sheet';
  if (doc.docType === 'base' || doc.wikiKind === 'bitable') return 'bitable';
  return 'doc';
}
```

放 `wiki-model.ts` 而非 `actions-dispatch.ts`（r2 MINOR-11）：`bridge.ts` 也要用它，而它现在只 import 4 个
exporter、**完全没 import `actions-dispatch`**；后者却 import 了 webcopy / summarize / screenshot / analytics /
badge / 6 个 exporter。为一个 3 行纯函数把这些全拉进来不值，`index.ts` 又同时 import 两者，容易出环。
`actions-dispatch.ts` 从 `wiki-model.ts` re-export 给测试用即可。

### 4.3 识别收口成一个公共入口

```ts
// actions-dispatch.ts
export interface PreparedDoc {
  doc: DocInfo | null;      // 已补齐 wikiKind；未识别时 null
  frameId?: number;         // 模型所在 frame；主 frame 或没探到 = undefined（注主 frame）
  error: Response | null;   // requireReady 的结果；非 null 时调用方直接返回它
}

/** 所有按文档类型限流的导出入口的统一前置：识别 → 就绪校验 →（只对 wiki）补齐承载类型与模型 frame。
 *  未就绪时**不做任何注入**（未授权私有化域名注不进去，白抛异常）。 */
export async function prepareFeishuDoc(tabId: number): Promise<PreparedDoc> {
  const doc = await detectDocForTab(tabId);
  const error = requireReady(doc);
  if (error || !doc) return { doc, error };
  if (doc.docType !== 'wiki') return { doc, error: null };
  // wiki：无条件探一次。即使 URL 已判出 wikiKind 也必须探，否则拿不到模型所在 frame。
  const frames = await probeFrames(tabId);
  const kind = doc.wikiKind ?? pickWikiKind(frames);
  const filled = kind ? { ...doc, wikiKind: kind } : doc;
  return { doc: filled, frameId: pickModelFrameId(frames, effectiveKind(filled)), error: null };
}
```

### 4.4 连锁影响逐条清点

| 位置 | 现状 → 改后 | 说明 |
|---|---|---|
| `requireReady` | 查 `UNSUPPORTED_EXPORT_TYPES[docType]`（该表是空的）→ **不动** | 没有全局不可导出的类型，与 `wikiKind` 无关 |
| `blockSheetOnly` | `docType==='sheets'` → `effectiveKind(doc)==='sheet'` | **正向变化**：wiki 表格点 PDF/HTML 从「1KB 空文件」变明确报错 |
| `blockBaseOnly` | `docType==='base'` → `effectiveKind(doc)==='bitable'` | **正向变化**：wiki 多维表格点 md 从空文件变「请用导出 Excel」。误判风险见 §2.4 / 风险 2 |
| `runExcelExport` | `docType!=='base'` 就拒 → `effectiveKind(doc)!=='bitable'` 才拒 | **硬约束 3 落地** |
| `runFeishuExport` md 分支 | `const isSheet = docType==='sheets'` → `effectiveKind(doc)==='sheet'`，调 `exportSheet(doc, frameId)` | 本 bug 的正主 |
| `index.ts` XHS/微信/附件 | 手写三件套 → 改用 `prepareFeishuDoc`，其余不动 | 不改则 wiki 表格照样走错管线 |
| `bridge.ts:505` | `if (docType==='sheets')` → 按 `effectiveKind` 三分支，bitable 明确报错 | 不改则 CLI 抓 wiki 表格照样空文件 |
| `resolveObjToken` | `docType!=='wiki'` 早返回 → **不动** | 加字段方案的最大好处 |
| `editor.ts:78` | `['docx','wiki'].includes(docType)` → **不动** | wiki 表格会被放行进编辑然后失败。既有行为，非本次引入，列为可选加固 |
| `cache-manager` / `CacheView` | 存/显示 `docType` → **不动** | wiki 表格缓存显示为 `wiki`，与 URL 一致 |
| `ContextZone.tsx` PageBar | 显示 `doc?.docType` → **不动** | 可选打磨（显示成 `wiki · 表格`），不进本次 |
| `sidepanel/actions.ts` | 5 个导出按钮全类型可见 → **不动** | 保持「点了给准确错误」，与 `/base/` 直链体验一致 |

## 五、改哪些文件、加什么分支

> 片段只给**真正要改的行**，函数名/变量名对着真实代码写；标「待验证」的是没在真机确认过的假设。

### 5.1 `feishu-detect.ts`

```ts
/** 从 URL 参数判断 wiki 节点里包的是什么。判不出返回 undefined，交给后台探测兜底。 */
export function wikiKindFromUrl(parsed: URL): DocInfo['wikiKind'] {
  const q = parsed.searchParams;
  if (q.get('sheet')) return 'sheet';
  if (q.get('table')?.startsWith('tbl')) return 'bitable';
  return undefined;
```

```ts
  frameId: number;
  sheetApp: boolean;    // 整页电子表格：spreadApp 存在且 sheets 列得出来
  sheetModel: boolean;  // 任意表格模型（含 docx 内嵌块的 window.spread）——只用于定位

export async function probeFrames(tabId: number): Promise<FrameSignals[]> {
  try {
    const results = await chrome.scripting.executeScript({
      target: { tabId, allFrames: true }, world: 'MAIN', func: probeInPage });
    return results.filter((r) => r.result)
      .map((r) => ({ frameId: r.frameId ?? 0, ...(r.result as Omit<FrameSignals, 'frameId'>) }));
  } catch { return []; }   // 注入失败（权限未生效、页面已关闭）：当作没探到，走普通文档路径

/** 注入 MAIN world，必须自包含、只读不写。光看 typeof 不够（见 §2.4），顺手确认模型结构。 */
function probeInPage(): { sheetApp: boolean; sheetModel: boolean; bitable: boolean } {
  const w = window as unknown as { spreadApp?: any; spread?: any; bitableStore?: any };
  let sheetApp = false, bitable = false;
  try { sheetApp = !!w.spreadApp && w.spreadApp.shell.viewModelManager.spread.sheets.length > 0; } catch {}
  try {
    const s = w.bitableStore?.services;
    const list = Array.isArray(s) ? s : s && typeof s === 'object' ? Object.values(s) : [];
    const base = (list as any[]).find((x) => x?.modelOperator?.base)?.modelOperator?.base;
    bitable = !!base?.blocks && Object.keys(base.blocks).length > 0;
  } catch {}
  return { sheetApp, sheetModel: sheetApp || !!w.spread, bitable };
}

/** 分类。⚠️ window.spread 一票都没有：普通 docx 的内嵌表格块也挂它（sheet.ts:150）。
 *  bitable 排前面因为特异性更高（电子表格页不会有 bitableStore）。 */
export function pickWikiKind(frames: FrameSignals[]): DocInfo['wikiKind'] {
  if (frames.some((f) => f.bitable)) return 'bitable';
  if (frames.some((f) => f.sheetApp)) return 'sheet';
  return undefined;
}

/** 定位：类型已定后找模型所在 frame。主 frame 优先且命中时返回 undefined（按现状注主 frame）。 */
export function pickModelFrameId(
  frames: FrameSignals[], kind: 'sheet' | 'bitable' | 'doc'): number | undefined {
  const has = (f: FrameSignals) =>
    kind === 'bitable' ? f.bitable : kind === 'sheet' ? f.sheetModel : false;
  const hits = frames.filter(has);
  if (!hits.length) return undefined;
  const pick = hits.find((f) => f.frameId === 0) ?? hits[0];
  return pick.frameId === 0 ? undefined : pick.frameId;
}
```

```ts
export function isBlankExport(markdown: string, assetCount: number): boolean {

}

/** 官方导出产物的空判据（服务端二进制，本地没有结构化中间结果）：零字节一律算空；

export function isBlankArtifact(base64: string, treatAsText: boolean): boolean {
  let bytes: Uint8Array;

  return new TextDecoder().decode(bytes).trim() === '';
```

### MAJOR-4 `spread` 回退的 `ok` 判据退化成「有没有数据」 → **部分采纳（附事实更正）**

**核对：主要论点属实**，逐条验过：① `read` 只在读格循环抛异常时为 `false`，而 `readGrid`（`sheet.ts:195-222`）
